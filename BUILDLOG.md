# Sera-vice — build log

A keychain/desk-pet companion device: an ESP32-S3 board with a tiny color
screen, an IMU, buttons and an RGB LED, running a mood-driven animated
face. Designed to be buildable by others — this log is the running record
that will become the public GitHub write-up. (Marcus's projects are
Unlicense, per his standing preference.)

- **2026-11-05** — The big day:
  - Custom mood firmware v1 built (PlatformIO + LOLIN's TFT_eSPI fork)
    and flashed. **Verified working on hardware**: faces, IMU triggers
    (shake/flip/stillness), buttons, mood LED.
  - Flashing lessons (hard-won, see `firmware-s3minipro/README.md`):
    this rev v0.2 chip will NOT boot at QIO/80MHz — stamp images
    DIO/40MHz; Debian's esptool package lacks its stub files (use
    `--no-stub` or a pip venv); Arduino IDE cannot flash a bare .bin —
    use merged full-flash images at 0x0.
  - Official Muse Gadget firmware also built for this board (custom
    overlay in the SDK): status-light class only — the avatar UI needs
    >=8MB flash and a closed board list, so no picture on this board.
    Kept for the future pendant build; pairing awaits an SDK token.
  - BLE chosen as the battle transport (protocol was designed for it);
    IR receiver demoted to optional.
  - Theme packs planned: replace the code-drawn faces with animated
    chibi sprites; packs upload over USB first, Wi-Fi fetch later.
  - Chibi bust enclosure designed (OpenSCAD, parametric) — ON HOLD
    pending caliper measurements. See `bust-v0/`.

- **2026-11-05 (evening)** — **Firmware v2 + first theme pack built**
  (host-verified; flashing is Marcus's step, not yet done):
  - **Custom partition table** (`firmware-s3minipro/partitions.csv`):
    single factory app slot 0x10000–0x200000 (1.94 MiB, no OTA), NVS
    preserved at 0x9000, and a dedicated **themepack partition,
    1 MB at fixed offset 0x200000**. Top 1 MB left spare.
  - **SRPK pack format v1** designed (spec lives at the top of
    `firmware-s3minipro/src/themepack.h`): magic "SRPK", version,
    frame-offset table, pack name, CRC32 (zlib) over the payload;
    frames are full 128×128 RGB565 portraits, one per mood in enum
    order — 8 frames = 262,240 bytes total.
  - **The v1 drawn faces are now the built-in fallback**: at boot the
    firmware validates the partition (header + full CRC); a valid
    pack's portraits replace the faces mood-for-mood, anything else
    and v1 runs exactly as before. All other v1 behaviour (mood
    engine, IMU triggers, buttons, LED, serial mood commands)
    unchanged.
  - **Cat-first serial pack receiver**, per Marcus's "why Python?"
    push: the serial stream is watched for the SRPK magic; a pack is
    staged in PSRAM and CRC-verified *before* the partition is
    erased, so a bad/truncated transfer changes nothing. Success
    prints `PACK OK <name>`, failure `PACK FAIL <reason>`. The whole
    upload UI is `stty -F /dev/ttyACM0 115200 raw -echo` then
    `cat pack.bin > /dev/ttyACM0`. esptool partial-write to 0x200000
    also works.
  - **Pack #1: "chibi-sera"** — 8 AI-generated portraits of Sera
    (source art in `themepacks/chibi-sera/`, framed torso-to-face per
    Marcus's art direction so expressions survive at 128×128: face
    large and dominant, green-top torso at the bottom edge), packed
    by `themepacks/build_pack.py` into `themepacks/chibi-sera.pack.bin`
    (262,240 bytes, payload CRC32 0xaea20d2e, `--verify` clean; the
    CRC was also cross-checked against a replica of the firmware's
    own CRC code, single-shot and chunked — match).
  - v2 image: `firmware-s3minipro/sera-vice-v2-st7789-dio40-full.bin`
    (544,256 bytes; app 468,784 bytes of the 1,984K slot). Build trap
    found: `board_build.flash_mode=dio` fails (the Arduino package
    ships no prebuilt dio_40m bootloader) — DIO/40 stamping stays at
    merge-bin time, as in v1.
  - One unverified-on-hardware point: RGB565 byte order through
    TFT_eSPI pushImage on this panel (v1 only ever used driver-drawn
    primitives). If reds/blues arrive swapped, the fix is a byte-swap
    in `build_pack.py` + a format bump — the flash test will say.

- 2026-11-06: **v2 flash test + theme pack color fix.** Marcus flashed
  v2 and uploaded the chibi-sera pack at work: the pack system worked
  end to end (face on screen, framing right), but every color was
  mangled - blue skin, lime-green hair, red flashes on the green top.
  Diagnosis (proven, not guessed): simulating a 16-bit byte swap on
  the source art reproduced his photo pixel-for-pixel in character -
  TFT_eSPI `pushImage()` consumes the frame buffer big-endian on this
  stack, and the pack stored each RGB565 pixel little-endian. It is a
  full byte swap, NOT a red/blue channel swap (a channel swap cannot
  turn brown hair green). Fix is pack-side only, exactly as scoped in
  the v2 notes: `build_pack.py` now stores each pixel high byte first;
  SRPK version stays 1, so the already-flashed v2 firmware accepts the
  rebuilt pack with no reflash and no erase. Rebuilt
  `themepacks/chibi-sera.pack.bin` (262,240 bytes, payload CRC32
  0x172d5d42, `--verify` clean), then verified end to end by running
  the new pack bytes through the hardware model calibrated on the
  photo: all 8 frames render back as the original art (max deviation
  7/255 per channel = RGB565 quantization only). Preview of the
  as-displayed frames: `themepacks/chibi-sera-preview.png`. Marcus's
  remaining step: re-`cat` the pack over serial and watch for
  `PACK OK chibi-sera`. Format spec comments in `build_pack.py` and
  `themepack.h` updated to record the byte order.
